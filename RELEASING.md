# Подготовка релиза Wakecup

Публикация — в [makhnevvitalik/Wakecup](https://github.com/makhnevvitalik/Wakecup). Версия берётся из `Info.plist`: сейчас **1.0.1**, сборка **12**.

## Локальная сборка

Используйте Mac с Xcode 26 или новее. В настройках Xcode выберите установленные инструменты командной строки. Сторонние пакеты Swift не нужны.

```sh
./build.sh
./test.sh
./build-release.sh
```

- `build.sh` собирает приложение для текущего Mac в `build/Wakecup.app`. Скрипт только собирает приложение.
- `test.sh` запускает автоматические проверки, подменяя операции управления питанием и авторизацией. Скрипт не меняет настройки сна и не устанавливает помощника.
- `test-ui.sh` отдельно проверяет вёрстку и может открывать окна. Запускайте его в тестовом сеансе macOS.
- `build-release.sh` создаёт универсальные ZIP и DMG для Apple Silicon и Intel в новом каталоге внутри `build/releases`. Настройка подписи описана в разделе [«Постоянная подпись»](#постоянная-подпись).

## Что проверяет CI

- Push в `main`, pull request в `main` и ручной запуск: REUSE, версия, сборка и `test.sh --ci` на macOS. CI проверяет подпись, флаг Hardened Runtime и отсутствие опасных entitlements. Проверку поведения при запуске проводят на Mac с включённой SIP: на проверенных GitHub-hosted runner SIP отключена.
- Тег `vMAJOR.MINOR.PATCH`: те же проверки, затем отдельная подписанная сборка в окружении `release-signing`.
- Тег должен точно соответствовать `CFBundleShortVersionString` и указывать на коммит из `main`.
- Итог — универсальные ZIP и DMG плюс `SHA256SUMS.txt`. Для `arm64` и `x86_64` проверяются архитектура, минимальная macOS 14, Hardened Runtime и соответствие встроенным хешам помощника.
- При успешной сборке нового тега CI сразу создаёт публичный релиз, как у Language Switcher Plus. Если релиз с таким тегом уже существует, CI обновляет его заголовок и заменяет ZIP, DMG и `SHA256SUMS.txt`. Описание и статус публикации сохраняются. У заранее созданного черновика можно проверить файлы перед ручной публикацией.

Обычные проверки не получают ключ подписи. CI запускает автоматические тесты без интерактивной проверки вёрстки.

## Постоянная подпись

Схема повторяет Language Switcher Plus: отдельный постоянный сертификат подписи кода для Wakecup и защищённое окружение GitHub. Сертификаты Plus/Dev не используются.

CI использует постоянный сертификат **Wakecup Release Signing**. Его публичный SHA-1 отпечаток:

```text
83DEFBD5CC931816072976562C3FDF2D2CE64085
```

Зашифрованную резервную копию P12 и пароль храните вне репозитория. На одноразовом runner CI временно доверяет сертификату для сборки. Пользователям импортировать этот сертификат в Связку ключей не нужно.

### Перенос или восстановление настройки

1. Используйте уже созданную зашифрованную копию P12. Не создавайте новый сертификат для каждого релиза: постоянная идентичность должна сохраняться. При переносе на другой Mac импортируйте эту копию; пароль возьмите из защищённого хранилища владельца сертификата.
2. В GitHub создайте окружение **release-signing** и включите Selected branches and tags: одно правило типа **tag**, имя **v***. Ветки к этому окружению не допускаются.
3. Добавьте в это окружение секреты:

   | Секрет | Значение |
   | --- | --- |
   | `MACOS_SIGNING_CERTIFICATE_P12` | P12, закодированный в Base64 |
   | `MACOS_SIGNING_CERTIFICATE_PASSWORD` | Пароль экспорта P12 |

4. Workflow уже закрепляет имя и отпечаток Wakecup. При необходимости их можно явно задать переменными того же окружения:

   | Переменная | Значение |
   | --- | --- |
   | `SIGNING_CERTIFICATE_NAME` | `Wakecup Release Signing` |
   | `SIGNING_CERTIFICATE_SHA1` | `83DEFBD5CC931816072976562C3FDF2D2CE64085` |

5. До загрузки ключа проверьте workflow и права окружения. Ключ используется только отдельным заданием выпуска на одноразовом GitHub-hosted runner. Скрипт проверяет отпечаток, временно импортирует ключ, подписывает и удаляет временную связку ключей при завершении.

P12, закрытые ключи, пароли и локальные связки ключей запрещено добавлять в Git. Игнорирование этих файлов — дополнительная защита, а не замена проверке содержимого.

Самоподписанный сертификат обеспечивает постоянную идентичность сборок, но **не делает приложение нотариально проверенным Apple** и не устраняет предупреждение Gatekeeper на чужом Mac. Установщик описан в README. Developer ID, secure timestamp, нотариальная проверка и stapling — отдельный будущий вариант; текущий pipeline их не выполняет.

### Почему нельзя подписать готовое приложение поверх

Сначала подписывается универсальный помощник. В каждую архитектуру приложения встраиваются SHA-256 всего файла помощника и CDHash соответствующей архитектуры. После объединения подписывается само приложение. Любая последующая переподпись помощника нарушает эту связь. Для подписанного выпуска нужно запускать всю сборку с нужным сертификатом:

```sh
WAKECUP_SIGNING_IDENTITY='83DEFBD5CC931816072976562C3FDF2D2CE64085' \
WAKECUP_REQUIRE_RELEASE_SIGNING=1 ./build-release.sh
```

Сертификат с закрытым ключом должен быть доступен в локальной связке ключей. Без настройки подписи обычный `./build-release.sh` создаёт только ad-hoc пакеты для проверки. При `WAKECUP_REQUIRE_RELEASE_SIGNING=1` выпуск без сертификата запрещён.

Помощник проверяет точный хеш приложения, поэтому новая сборка может требовать обновления установленного помощника **даже с постоянным сертификатом**. Это не нужно скрывать или обещать отсутствие запроса пароля после обновления.

## Проверка перед выпуском

1. Запустите `./test.sh` и `./build-release.sh`. Посмотрите итоговый diff и убедитесь, что нет ключей, паролей, локальных путей пользователя и файлов сборки.
2. Проверьте `python3 Tools/release_metadata.py --tag v1.0.1`, описание `.github/release-notes.md`, инструкции и условия лицензии. Для следующего релиза обновляйте версию, номер сборки и описание согласованно.
3. Проверьте локальные подписанные пакеты по шагам 5–8 до отправки тега, если CI должен опубликовать релиз сразу. Для проверки пакетов CI перед публикацией заранее создайте черновик с этим тегом. После отдельного разрешения отправьте исходники и тег в GitHub.
4. Дождитесь всех заданий CI. Без настроенного окружения подписи релизное задание завершится ошибкой, а не выпустит ad-hoc приложение.
5. Проверьте контрольные суммы пакетов командой `shasum -a 256 -c SHA256SUMS.txt`. На Mac с включённой SIP запустите `./Tests/HelperRuntimeTests.sh "/путь/к/Wakecup.app"` для приложения из пакета. Проверьте установку из DMG и ZIP, первый запуск, RU/EN, таймер, ручную остановку и работу от аккумулятора.
6. Отдельно проверьте режим с закрытой крышкой: запрос пароля, установку помощника, работу без повторного запроса, обновление и удаление. Подтвердите восстановление обычного сна после остановки. Эти проверки меняют реальные системные настройки и не заменяются unit-тестами.
7. На установленной сборке со встроенным экраном задайте сочетание «Вернуть яркость» и включите режим «Без подсветки». Проверьте, что сочетание возвращает прежнюю яркость и таймер продолжает работу. Повторно включите режим и проверьте возврат подсветки клавишей увеличения яркости. Отдельно проверьте возврат яркости после остановки таймера и после завершения Wakecup.
8. Проверьте пакеты на Apple Silicon и Intel. Кросс-компиляция проверяет структуру и подпись Intel-файлов, но не заменяет запуск на Intel Mac. Минимальная macOS 14 объявлена в метаданных; живой запуск на ней также проверяется отдельно.
9. Если использовали черновик, опубликуйте его после приёмки. Для публичного релиза проверьте, что скачиваются все файлы. Проверка обновлений в приложении видит только публичные стабильные релизы.
